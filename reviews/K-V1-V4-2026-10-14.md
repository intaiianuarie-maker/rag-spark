### Findings

#### F1 — Malformed WORKSPACE_MODEL_CONFIG silently drops the sensitive veto (fail-open)
- SEVERITY: Med
- path: packages/models/router_config.py:346-348 (also :353)
- what (OBSERVED): an unparseable/blank `WORKSPACE_MODEL_CONFIG` env returns
  `None` after a warning. Every caller then reads
  `workspace.sensitive if workspace else False` (apps/api/app/ask/router.py:158;
  the search path: apps/api/app/search/search.py:224
  `_egress_sensitive = bool(_ws_config.sensitive) if _ws_config is not None else False`).
- why it matters: T-A01/T-V1-029 exist so a sensitive workspace can never
  egress embeddings or use a cloud model. A JSON typo in the operator config
  flips the veto off — the "fail-open on missing/invalid config" shape the
  review brief weights heavily. A workspace marked sensitive stops being
  protected with only a log line, and no test exercises the unparseable case
  (grep `workspace_model_config_unparseable` in tests: no matches).
- fix shape: distinguish "no entry for this workspace" (None, healthy) from
  "config present but unparseable" (raise a typed config error, or at minimum
  treat `*` as sensitive when the payload is unparseable); add a unit test that
  a malformed payload leaves the veto on.

#### F2 — Citation verification silently degrades to None on lookup construction failure
- SEVERITY: Med
- path: packages/answer/factory.py:170-175
- what (OBSERVED): `PostgresChunkLookup()` is built inside
  `try: ... except Exception: pass`, so any construction error (DB URL absent,
  import error, driver misconfig) leaves `chunk_lookup = None`; the engine then
  runs the legacy existence/scope-only path (factory.py:194-195) with no log line.
- why it matters: the store-backed existence check, scope revalidation, and
  lifecycle revalidation of citations are what make "citation resolves to a
  real chunk in the caller's workspace" enforceable. A transient/misconfigured
  store silently weakens that guarantee on every /ask until restart.
- fix shape: log at warning with the exception type (never a bare pass), and
  fail closed (typed 503 / `RETRIEVAL_UNAVAILABLE`) when the store lookup is
  required for ask and cannot be constructed — or disclose the degradation in
  the Answer rather than leaving it invisible.

#### F3 — API-key principals skip the user-active check
- SEVERITY: Med
- path: apps/api/app/authz/principal.py:108-118 vs apps/api/app/auth/service.py:108-109, :143
- what (OBSERVED): `_principal_from_key` builds the Principal with
  `is_active=True` hardcoded; `get_active_key` checks only the key (revocation,
  expiry, hash — auth/keys.py:126-139) and never joins the user. Password login
  and refresh both reject `not user.is_active` (service.py:108-109, :143).
- why it matters: deactivating a user does not invalidate that user's
  workspace API keys — an offboarding gap on the machine-to-machine path.
- fix shape: look up the key's user (in `get_active_key` or
  `_principal_from_key`) and return None when the user is absent/inactive.

#### F4 — Migration failure at boot is warn-and-continue
- SEVERITY: Low
- path: apps/api/app/main.py:47-56
- what (OBSERVED): a `run_migrations` failure is logged at warning and lifespan
  proceeds to serve.
- why it matters (INFERRED): an API serving traffic on a stale/partial schema
  500s per query rather than failing fast at boot; acceptable if
  `migrations_on_boot` is deliberately non-fatal, but the coupling is invisible
  to /ready.
- fix shape: refuse startup when migrations fail and `migrations_on_boot` is
  set, or surface a `migrations` field on /ready.

#### F5 — Date filter applied after top-k truncation
- SEVERITY: Low
- path: apps/api/app/search/search.py (docstring :11-18, `build_search_filter`
  :108-130, post-filter at request handling :257)
- what (OBSERVED): `date` is a post-retrieval predicate while merged
  type/source/collection are pushed pre-ranking; the module discloses this
  ("narrows (never widens)").
- why it matters: `query=foo filters.date=2026-01-01..2026-12-31` retrieves the
  unfiltered top-k first, then filters, so valid matches outside the top-k are
  dropped — a silent under-return for combined filters.
- fix shape: disclose per-request (e.g. `filters_truncated: true` when the
  narrowed set is empty but the pre-filter result was not), or push date range
  into store predicates where the metadata key is known.

## V2 — Graph leg (FLAG-OFF), research/agents consumer wiring

Paths walked: packages/graph/{factory,retriever,consumer,dispatch}.py,
packages/graph/sqlite_store.py (targeted greps),
packages/retrieval/orchestrator.py (_graph_leg, REQUIRED_LEGS, fusion),
packages/answer/{factory,hydration,engine}.py,
packages/agents/{tools,worker,queue,runtime}.py,
packages/research/{engine,external_connector}.py.

### Verdict: CONDITIONAL

FLAG-OFF is genuinely enforced (returns None, not a stub; v1 byte-identical
path) and the graph leg is optional in the failure taxonomy — but the graph
wiring reaches into the v1 critical path in ways that are silent, and the code
explains the eval asymmetry only partially.

### Findings

#### G1 — Graph-module import or bad GRAPH_MODE breaks /ask and /search
- SEVERITY: High
- path: packages/answer/factory.py:92 and :117-126, packages/graph/factory.py:98-105
- what (OBSERVED): `create_orchestrator()` — the constructor every /ask and
  /search request builds through — imports `graph.factory` and calls
  `create_graph_retriever()` on **every** construction. When `GRAPH_MODE` is a
  typo (neither off nor rule/llm), `create_graph_retriever` **raises
  ValueError** (factory.py:101-105). There is no try/except in
  `create_orchestrator`, and the ask route builds the engine *after* auth and
  model resolution (apps/api/app/ask/router.py:246).
- why it matters: "FLAG-OFF means v1 unchanged when the flag is off" holds for
  the happy flag-off value, but any other GRAPH_MODE string (or a packaging
  failure of packages/graph, which `packages/answer` now imports
  unconditionally) turns /ask and /search into hard 500s. Readiness reads
  `graph_store` red on the invalid mode but the API is already broken at the
  same instant — the honest-disclosure machinery is downstream of the crash.
  INFERRED: alerting that keys on the graph value alone will misattribute the
  outage; rollback of a graph release cannot be verified without reading
  request logs.
- fix shape: wrap the call `try/except Exception -> None` with a loud
  `logger.error` (a dead graph leg degrades to flag-off behaviour, which is
  what GRAPH_MODE=off does anyway), or gate the call on
  `graph_mode(env) in GRAPH_MODES_ON` so an invalid value is red in readiness
  only; and make `packages/graph` a required dependency of the API since the
  answer factory imports it.

#### G2 — New global module state in agent runtime; graph attribution double-hides errors
- SEVERITY: Med
- path: packages/agents/runtime.py:728-766 (`_PERSISTED_STATES`,
  `_PERSISTED_USAGES`, `_APPROVALS`, `_WAITING`, `_PERSISTED_RUNS`),
  packages/agents/worker.py:68, packages/answer/engine.py:645-658
- what (OBSERVED): the runtime keeps run state in **process-global dicts**
  keyed by run_id, and the worker consults the runtime's private global.
  Separately, the graph-attribution block swallows exceptions twice — inner at
  engine.py:647 (logged warning) plus an outer `except Exception: pass` at
  :657-658 with **no log at all**.
- why it matters: global state means multi-worker/multi-process deployment
  loses state on restart and can cross-wire run_ids between processes; the
  silent outer except can hide failure to record graph provenance — attribution
  is the eval data that decides flag-on, i.e. exactly the numbers in the
  prior-review asymmetry finding (-0.081 / +0.250).
- fix shape: move run state behind a store interface (the worker already has a
  checkpoint store); replace the bare pass with a logged warning.

#### G3 — Graph fusion weights explain the eval asymmetry only partially
- SEVERITY: Med
- path: packages/retrieval/orchestrator.py:586-597, packages/graph/retriever.py:27-159
- what (OBSERVED): graph items enter RRF as a fourth equally-weighted ranking
  (`rankings.append` at :586-590); graph's internal relevance is a constant
  `score=1.0` local / `0.9` global, and `chunk_scores` are mention counts, not
  evidence quality. Global search matches on raw token overlap with community
  summaries (retriever.py:125-133).
- why it matters (INFERRED read of the −0.081/+0.250 asymmetry): graph helps
  multi-hop because the subgraph surfaces entity/relation chunks that the
  dense/lexical legs never retrieve; it hurts table QA because each graph item
  displaces a top-k slot with a chunk ranked by *graph traversal* rather than
  table-cell relevance — local search adds every evidence chunk of every
  matched entity at uniform score 1.0 (retriever.py:57-72), so 5 matched
  entities can flood 5× the dense candidates. There is no per-mode damping, no
  dedup against dense/lexical hits before fusion, and no table-aware
  down-weighting anywhere.
- fix shape (evidence, not code demands): damp graph's fusion weight and/or cap
  graph's contribution per mode; dedupe graph chunk refs against dense/lexical
  hits before fusion so graph contributes only *new* chunks.

#### G4 — Routing-hint text exclusion depends on the hydrator being present
- SEVERITY: Low
- path: packages/graph/retriever.py:161-217, packages/answer/hydration.py:259-286
- what (OBSERVED): graph items are emitted carrying
  `content = "[Knowledge Graph Context]\n{summary}"` with a `chunk_id`; the
  synthesized text reaches the prompt unless the hydrator replaces it, and the
  hydrator is a **pass-through when `chunk_lookup is None`** (hydration.py:259-260).
  With a lookup present, refless and unresolvable items are dropped (:268-286)
  and `routing_hint` items never ground citations (verification.py:28-29).
- why it matters: safe in the wired configuration, but the safety is a property
  of the *hydrator being present*, not of the graph items. If the canonical
  lookup degrades to None (see V1 F2), graph routing-hint text would flow into
  the model prompt as if it were retrieved evidence.
- fix shape: emit graph items with empty `content` + `routing_hint` marker so
  no consumer can mistake them for evidence; assert refless items are dropped
  before prompt build.

#### G5 — Agent worker: silent swallow of missing context and recovery failures
- SEVERITY: Low
- path: packages/agents/worker.py:53-59 and :116-119
- what (OBSERVED): a claimed run with no in-memory context parks with
  `MISSING_CONTEXT` (visible), but `queue.park` is wrapped in
  `except Exception: pass` (:57-58) and `recover_expired()` failures are
  swallowed entirely (:118-119); the ack/park decision for a run that could
  not execute carries no log line.
- why it matters: a broken broker client makes park/recovery fail silently
  while `run_once` still returns the run_id — an operator watching job outcomes
  sees runs "handled" that never were (the "job reports success while doing
  nothing" shape).
- fix shape: log every swallowed branch at warning with the error type, and
  surface recovery failures into the supervisor loop (copy the graph
  consumer's visible-restart model, consumer.py:323-380).

#### G6 — `test:` queue-prefix fallback in a production path
- SEVERITY: Low
- path: packages/agents/queue.py:42-47
- what (OBSERVED): `_prefix()` falls back to the literal string `"test:"` when
  `get_settings()` raises (any settings-construction error in a
  production-shaped process), making the queue key `agent:test:queue`.
- why it matters: a misconfigured production process silently shares an agent
  queue namespace with test infrastructure (cross-env claims/parked runs).
- fix shape: propagate the exception, or use a `production:`/`unknown:` prefix
  that cannot collide with tests.

### Genuinely good enforcement (OBSERVED, cited)

- Factory returns `None` (never a stub) when off, and raises for an unknown
  mode rather than silently disabling: packages/graph/factory.py:93-105.
- Graph leg is OPTIONAL in the failure taxonomy for every mode, so a graph
  outage degrades and never fails a request closed:
  packages/retrieval/orchestrator.py:166-178 (`REQUIRED_LEGS`), legs failure
  reported per-leg.
- Defense in depth: every leg's items are re-filtered through `_in_scope`
  before fusion (R-004), graph items included: orchestrator.py:571-579.
- Extraction-mode dispatch refuses an unknown mode and refuses to build an

  :100-112.
- Consumer supervision is countable and visible: bounded backoff, restarts

  packages/graph/consumer.py:323-390.
- Graph store queries are workspace-scoped in SQL (`WHERE workspace_id=?`

  applied.
- Research engine raises on provider/parse failure rather than fabricating a
  plan: packages/research/engine.py:104-111; external fetch refuses without an

- Agent tools strip model-supplied `workspace_id`/`acl_scope` kwargs before

### Verdict: ACCEPT

### Findings

#### W3-1 — Flag-off default factory is dead in production callers
- SEVERITY: Low
- path: packages/workflow_engine/adapters/v3_adapter.py:171-176
- what (OBSERVED): the flag-off branch calls `default_factory()` or imports
  and instantiates `ProductionNodeExecutor`; no production caller passes a
  factory (the only `WorkflowExecutor(...)` in apps/ constructs a
  `ProductionNodeExecutor` directly — router.py:663), so each
  `resolve_node_executor()` call builds and discards a fresh executor.
- why it matters: no runtime harm (constructors are pure, no I/O); the dead
  seam is misleading for readers hunting the DI point.
- fix shape: route production through `resolve_node_executor` with an injected
  default factory, or delete the branch.

#### W3-2 — Authoring run endpoint converts every failure into a FAILED run with raw `str(exc)`
- SEVERITY: Med
- path: apps/api/app/workflows/router.py:677-687 (and :656-657)
- what (OBSERVED): the whole compile+execute block is wrapped in
  `except Exception`; on failure the handler synthesizes a `WorkflowRun` with
  `error=str(exc)` and `finished_at=now`, and returns HTTP 200 with that run.
- why it matters: "invalid definition" (a 4xx-shaped failure) is reported with
  raw exception text on the wire (paths/SQL may leak) and is shape-indistinguishable
  from a node failure; the caller cannot tell bad input from a broken run.
- fix shape: map compile/validation errors to 422 with the safe registry
  message, keep `str(exc)` server-side in logs, and put a code on the run error.

#### W3-3 — Run executors are process-global: cancel silently no-ops after restart
- SEVERITY: Low
- path: apps/api/app/workflows/store.py:70, :140-147, :175-178, :189-191
- what (OBSERVED): `_executors` is an in-memory dict; `cancel_run` consults it
  while run rows persist to SQLite. After a restart the row exists but the
  executor does not.
- why it matters: a cancel request then returns success-shaped output while
  changing nothing (same no-op shape as V2 G5).
- fix shape: resolve cancel through a durable executor registry or return an
  honest 409/4xx when no live executor can service the request.

#### W3-4 — Adapter delegation returns the runner's raw value unvalidated
- SEVERITY: Low
- path: packages/workflow_engine/adapters/v3_adapter.py:150-151
- what (OBSERVED): `execute_node` increments `dispatches` then returns
  `await self._agent_runner(request)` verbatim; no check that the result is the
  declared `dict[str, Any]` output-ports mapping.
- why it matters: the executor's byte cap still applies downstream
  (executor.py:1189-1197), so the risk is shape confusion (a non-mapping
  propagating as port data), not unbounded output.
- fix shape: validate the returned value is a mapping of output ports and raise
  a typed adapter error otherwise.

### Verdict: ACCEPT (removal verified complete in production paths)

FakeNodeExecutor removal is complete on every production construction site,
unsupported capabilities and node types refuse loudly with names, and the
executor's timeout/retry/output-cap/idempotency machinery is honest.

### Findings

#### V4-1 — Approval gate validates against a different manifest than execution
- SEVERITY: Med
- path: apps/api/app/workflows/router.py:582-585 vs
  packages/workflow_engine/manifest.py:19-36
- what (OBSERVED): approval validates with a locally-invented manifest
  (`enabled_capabilities={"knowledge_search","document_read","llm_generate"}`)
  while execution uses `PRODUCTION_CAPABILITY_MANIFEST`
  (`{"llm","transform","condition","agent","calculator","knowledge_search","knowledge_read"}`).
  The sets are neither subset nor superset of each other: `document_read` and
  `llm_generate` exist in the production set nowhere; `transform`, `condition`,
  `agent`, `calculator`, `knowledge_read` are missing from the approval gate.
- why it matters: a revision whose nodes require `transform` can pass approval
  (the gate ignores it) and then fail at execution; a node requiring
  `document_read` can be rejected at approval for a capability the runtime
  never uses. The two halves of the product disagree about what "approved"
  means — the same drift the store_discipline module takes explicit care to
  avoid (store_discipline.py:8-9).
- fix shape: import and reuse `PRODUCTION_CAPABILITY_MANIFEST` (or inject the
  same manifest the executor uses) so approval and execution cannot diverge.

#### V4-2 — Migration artefact is draft-only; revision persistence not wired to the running app
- SEVERITY: Med
- path: packages/workflow_engine/migrations/README.md (status "DRAFT — applied
  by nobody"), migrations/0001_workflow_draft_revisions.up.sql:5-8,
  apps/api/app/workflows/store.py:82-93
- what (OBSERVED): the draft migration explicitly applies nothing ("runs no
  upgrade and writes nothing to any live database"), while the API's draft
  store defaults to an in-memory store with an optional SQLite draft store
  gated on env/config.
- why it matters: run and approval rows persist to SQLite (store.py:19-48) but
  draft *revisions* are in-process unless the SQLite draft store is explicitly
  enabled — a restart between approve and run loses the very revision the
  approval referenced, which is the exact scenario the migration README gives
  as its motivation. Whether a deployment enables it is invisible in code, and
  no readiness probe covers it.
- fix shape: apply the migration (or wrap it as an alembic revision), make the
  persistent draft store the default, and disclose "draft store in-memory" on
  /ready or /version when so configured.

#### V4-3 — Checkpoint append failure is counted but neither logged nor surfaced
- SEVERITY: Low
- path: packages/workflow_engine/executor.py:568-571 (`except Exception:
  self.checkpoint_failures += 1`)
- what (OBSERVED): a failed checkpoint increments a counter, the run continues;
  nothing logs, and no caller in apps/ reads `checkpoint_failures`.
- why it matters: the in-process idempotency ledger still protects a
  redelivery, but a worker restart after a failed checkpoint silently
  re-executes settled nodes — a durability gap with no trace.
- fix shape: log at the increment site (run_id + error type) and expose the
  counter in the run response or an observability surface.

#### V4-4 — Run-level failure text reaches the client unfiltered (cross-ref W3-2)
- SEVERITY: Low
- path: apps/api/app/workflows/router.py:677-687
- what (OBSERVED): `error=str(exc)` is persisted into the run row and returned
  in the response body.
- why it matters: raw exception strings can carry paths/SQL; callers are
  workspace-authorized, hence Low.
- fix shape: persist a code, keep detail server-side, mirror the
  `core.errors.error_detail` taxonomy used by ask/search.

### Genuinely good enforcement (OBSERVED, cited)

- Unsupported capabilities/node types refuse loudly with the missing names and
  available set, at both compile and runtime: manifest.py:12-18,
  production_executor.py:57-76.
- Permanent node errors (`NotImplementedError`) do not retry; transient ones
  retry with bounded backoff; timeouts name the bound and the observed value;
  oversized outputs are refused with the byte count: executor.py:1158-1200.
- A node returning an error payload is a failure, never absorbed into run
  outputs: executor.py:1201-1204.
- The idempotency ledger replays before execution, and a key presented for
  different work raises rather than silently re-executing: executor.py:1140-1149.
- Mid-node cancellation settles to CANCELLED with a recorded reason instead of
  a phantom COMPLETED: executor.py:809-819.
- Checkpoint sequence regression is refused (ahead-of-expected checkpoint):
  checkpoint.py:289-295.

## Cross-cutting

### Verdict: CONDITIONAL

Failure-honesty is enforced at the leg/route/store boundaries with tests that
match their names, but silent degradation at three seams (workspace config,
chunk lookup, queue prefix) recurs across all four versions.
