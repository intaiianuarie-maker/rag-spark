# ASTRA independent V1–V4 review — 2026-10-14

Scope: current on-disk source, reviewed solo in V1 → V2 → V3 → V4 → cross-cutting order. Static inspection only; no tests, services, live endpoints, git history, handoffs, or evals were executed/read. Product files were read-only. This report is the only filesystem write. OBSERVED describes source behavior; INFERRED describes its consequence under the stated conditions. Line references are repository-relative. Fix shapes are recommendations, not applied changes.

## V1 — core RAG, upload-only

**Verdict REJECT — the local-only policy does not constrain embedding egress, and two retrieval safeguards fail to carry their intended guarantees through production calls.**

### V1-01 — SEVERITY High — sensitive/local-only queries still reach cloud embeddings

**Evidence:** `packages/models/router_config.py:455` selects a local generation model for sensitive workspaces; `apps/api/app/ask/router.py:246` builds an engine using only that selected model. `packages/answer/factory.py:40` restricts the generation transport, while `packages/answer/factory.py:67` independently constructs an unrestricted OpenRouter embedder. `packages/retrieval/orchestrator.py:303` embeds the question. `packages/models/adapters/openrouter_provider.py:401` selects the OpenRouter cloud endpoint when its key exists; `packages/models/adapters/openrouter_provider.py:801` sends the input text to `/embeddings`, and `packages/models/adapters/openrouter_provider.py:863` passes the complete question as that input.

**OBSERVED / what:** The sensitive-workspace decision reaches the generation provider, but neither the retrieval factory nor the embedding provider receives it. Semantic/hybrid Ask requests embed the question before generation, including when the chosen generation model is local.

**INFERRED / why it matters:** With a configured cloud embedding key, a question submitted to a sensitive/local-only workspace leaves the local boundary despite the local generation policy. This is a confidentiality defect; local generation alone does not protect question contents. This is a source-grounded conditional path, not a claim that a live secret or transmission was inspected.

**Fix shape:** Carry workspace egress policy into retrieval and embedding selection. Require a verified local embedding transport for local-only workspaces, or refuse semantic/hybrid retrieval before any embedding request when none is available. Exercise the real engine factory with transport spies and a sensitive workspace, including the configured-cloud-key case.

### V1-02 — SEVERITY Med — production dense searches bypass query/collection identity compatibility

**Evidence:** `packages/retrieval/orchestrator.py:310` calls the dense store with collection/vector/filter but no query identity. `packages/retrieval/adapters/qdrant_store.py:1011` makes identity optional, and `packages/retrieval/adapters/qdrant_store.py:1034` verifies compatibility only when it is supplied. The production embedder has identity attributes at `packages/models/adapters/openrouter_provider.py:378`. The negative test supplies identity explicitly at `tests/unit/test_embedding_identity_boundary.py:327`; the source-string wiring test at `tests/unit/test_embedding_identity_boundary.py:375` checks that verifier calls occur somewhere in the adapter.

**OBSERVED / what:** The adapter rejects an unknown collection identity, but a known collection is queried without comparing its model/provider/revision to the actual production query embedder. The cited tests cover the explicit adapter argument and source presence, not propagation through the production orchestrator.

**INFERRED / why it matters:** An explicitly selected collection built with another same-width embedding model/revision can produce plausible but meaningless nearest neighbors instead of refusing. Dimension compatibility does not establish embedding-space compatibility. Passing the adapter tests cannot establish that the serving path enforces this invariant.

**Fix shape:** Derive identity from the provider and observed query-vector dimension, make it required at the production search boundary, and thread it through the dense-store interface. Test a mismatched collection via the real orchestrator and assert that Qdrant receives no query.

### V1-03 — SEVERITY Med — canonical lookup outages are reported as missing evidence

**Evidence:** `packages/answer/adapters/postgres_lookup.py:189` catches every bulk lookup exception and returns an empty mapping at line 194. `packages/answer/hydration.py:207` consumes that mapping; `packages/answer/hydration.py:211` treats absent rows as missing/deleted/superseded. `packages/answer/engine.py:195` reads only the retrieval-leg outcome, then calls the model at line 244. Empty hydrated evidence becomes `INSUFFICIENT_EVIDENCE`/`EVIDENCE_MISSING` at `packages/answer/engine.py:318`; lookup loss during verification becomes `CITATION_INVALID` at `packages/answer/engine.py:360`.

**OBSERVED / what:** A database/query failure during canonical hydration has the same return value as genuinely missing chunks. No typed failure reaches the retrieval outcome or Ask route from this lookup.

**INFERRED / why it matters:** A lookup-specific SQL/schema error or an outage after successful retrieval can yield an ordinary evidence refusal, concealing that a required dependency failed. The context-hydration case also spends a model call with empty context. Content access remains closed; the defect is incorrect availability/status reporting.

**Fix shape:** Propagate a typed canonical-store-unavailable error and map it to the registered unavailable status/503. Keep missing/deleted rows as ordinary misses. Test retrieval success followed by a failing hydration query and assert no generation call.

**Verified enforcement:** Workspace authorization precedes factory/retrieval calls (`apps/api/app/search/search.py:208`, `apps/api/app/ask/router.py:200`). Vector and lexical stores filter workspace scope before store ranking (`packages/retrieval/adapters/qdrant_store.py:316`, `packages/retrieval/adapters/pg_fts.py:144`), with another scope gate before fusion (`packages/retrieval/orchestrator.py:490`). Canonical hydration rejects foreign-workspace citations (`packages/answer/hydration.py:215`), and verification freshly rechecks citation lifecycle before return (`packages/answer/verification.py:1168`). Missing/shipped JWT signing secrets are rejected (`apps/api/app/auth/config.py:91`, `apps/api/app/auth/config.py:143`); session ownership binds the JWT subject (`apps/api/app/authz/principal.py:91`). Ingestion refuses READY unless both mandatory store writes were verified (`apps/worker/jobs/ingest_pipeline.py:1076`). Serving-name helpers explicitly reject an unset/default promotion collection (`packages/retrieval/serving.py:118`, `packages/retrieval/serving.py:125`); this observation alone does not establish startup enforcement.

## V2 — graph flag-off, agents, research, consumers

**Verdict REJECT — queued agents lack a production consumer, research verification uses a test source, and graph jobs can lose work or report success after total extraction failure.**

### V2-01 — SEVERITY High — accepted agent runs have no consumer in the shipped worker

**Evidence:** `apps/api/app/agents/lifecycle_routes.py:389` persists the run, enqueues it at line 393, and returns 202 at line 400. `apps/worker/jobs/agent_worker.py:42` defines the lifecycle worker and `apps/worker/jobs/agent_worker.py:227` defines its loop. `apps/worker/worker/main.py:55` starts ingestion and `apps/worker/worker/main.py:63` optionally starts graph consumption, then waits for shutdown at line 79. `apps/worker/Dockerfile:25` runs that main module. A targeted symbol search of apps/packages/scripts/compose found no invocation of the agent lifecycle loop outside its definition.

**OBSERVED / what:** The reviewed production entrypoint starts no agent lifecycle task, despite the API accepting durable queued runs.

**INFERRED / why it matters:** Under the shipped entrypoint, accepted queued runs remain queued indefinitely. Unit tests that manually instantiate the worker do not prove that the product consumes its queue. An independently provisioned consumer outside this tree was not inspected and cannot be assumed.

**Fix shape:** Start and supervise the lifecycle consumer in the production entrypoint, with its own liveness/readiness signal and shutdown handling. Refuse admission when this capability is unavailable. Verify that an API-submitted run is consumed by the actual packaged entrypoint.

### V2-02 — SEVERITY High — production research authenticates retrieved text against its own test cache

**Evidence:** `apps/api/app/agents/research.py:78` constructs the runner with only an LLM. `packages/agents/research_pipeline.py:104` defaults to `InMemoryChunkSource`, explicitly described as a test source at `packages/agents/verifier.py:45`. Search/read tool outputs populate that source at `packages/agents/research_pipeline.py:264` and line 283. The verification pass uses that same source at `packages/agents/research_pipeline.py:333`; `packages/agents/verifier.py:143` reads its content. The deletion test manually tombstones this fake before execution (`tests/unit/test_v3_research_pipeline.py:350`, `tests/unit/test_v3_research_pipeline.py:354`).

**OBSERVED / what:** The production factory does not inject an authoritative chunk/lifecycle source. It copies returned tool snippets into a test dictionary, then uses that dictionary to authenticate evidence. The dictionary receives no document deletion/version notifications.

**INFERRED / why it matters:** A chunk deleted/replaced after tool retrieval can still ground a reported research claim. A verifier checking the same cached text does not establish that the citation currently resolves to a real accessible stored chunk. The cited deletion test proves behavior for a manually marked fake, not live canonical deletion revalidation.

**Fix shape:** Require an authoritative scoped chunk source in the production runner, with document version/lifecycle checks immediately before report return. Keep the cache only for candidate text. Test deletion or replacement between search and verification through the production factory.

### V2-03 — SEVERITY Med — lifecycle checkpoint resume is disconnected from the stored checkpoint

**Evidence:** `apps/worker/jobs/agent_worker.py:116` loads `_checkpoint` but line 120 invokes the runtime without using it. `packages/agents/runtime.py:194` defaults its separate checkpoint adapter to `InMemoryStepStore`; `packages/agents/runtime.py:223` suppresses checkpoint-save exceptions. `packages/agents/runtime.py:686` loads through that separate adapter and starts fresh at line 718 when no checkpoint is found. `tests/unit/test_agent_lifecycle.py:718` claims worker kill/checkpoint recovery, but seeds a checkpoint at line 758 and finishes using a one-answer mock at line 781; its assertions at lines 792–797 check queue drain and completion, not restored usage/history or suppressed repeated work.

**OBSERVED / what:** Supplying the lifecycle worker's durable checkpoint store does not inject it into the runtime. Loading the worker checkpoint has no effect on execution. Missing/failed runtime checkpoint reads permit a fresh start.

**INFERRED / why it matters:** Restart/redelivery can repeat tool calls and reset previously consumed budgets instead of resuming. The named recovery test can pass while checkpoint restoration is absent; it proves lease recovery and eventual completion only.

**Fix shape:** Use one explicit durable checkpoint contract across the worker/runtime, restore state and usage before any dispatch, and distinguish a fresh run from a failed checkpoint load. Assert restored counters/history and no repeated side effect in a fresh-process recovery test.

### V2-04 — SEVERITY Med — graph fusion counts duplicate votes and ranks evidence by identifier

**Evidence:** `packages/graph/retriever.py:34` seeds on query tokens and traverses neighbors at line 52. It emits sorted evidence IDs with uniform local score (`packages/graph/retriever.py:79`), while global search admits every community with any substring overlap (`packages/graph/retriever.py:100`) and also sorts evidence IDs at line 111. `packages/retrieval/orchestrator.py:385` concatenates local and global results into one leg. `packages/retrieval/orchestrator.py:509` preserves duplicate keys in that leg's ranking, and RRF adds a contribution for every occurrence (`packages/retrieval/orchestrator.py:245`). The default final context window is six items (`packages/retrieval/interfaces.py:35`).

**OBSERVED / what:** The same chunk can receive two graph contributions within one nominal retrieval leg. Graph rank is derived from chunk-ID order and local/global concatenation, not evidence relevance; broad community matches have no query-specific top-k selection before fusion.

**INFERRED / why it matters:** Broad graph candidates and duplicate votes can displace precise table rows in a short context, while neighbor expansion can recover connecting evidence needed for multi-hop questions. This is a plausible source explanation for the user-supplied table-QA −0.081 / multi-hop +0.250 asymmetry, not a reproduced causal measurement. The supplied magnitudes were not independently verified, and no evals were read.

**Fix shape:** Deduplicate each leg before RRF, score/rank graph evidence by query relevance, bound global expansion, and gate or weight graph use by query/task suitability. Validate table and multi-hop strata separately before enabling graph by default.

### V2-05 — SEVERITY Med — total LLM graph-extraction failure is acknowledged as success

**Evidence:** `packages/graph/adapters/lightrag_extractor.py:192` converts provider errors into per-chunk error records and continues; its result returns those errors at line 217. `apps/worker/jobs/graph_extraction.py:167` only logs extraction errors, then upserts at line 231 and returns counts at line 251. `apps/worker/jobs/graph_extraction.py:301` treats that return as success and deletes the job payload at line 303.

**OBSERVED / what:** If every chunk fails provider extraction, the worker can write an empty extraction, report zero counts, and remove the durable job without retrying or retaining an explicit failed/partial status.

**INFERRED / why it matters:** A graph-provider outage can permanently omit a document from the graph while its graph job looks successfully handled. Per-chunk warnings do not preserve a recoverable failed job. Ordinary zero-entity extraction and zero-successful-chunk extraction are conflated.

**Fix shape:** Track successful versus failed chunk extraction explicitly. Fail/retry when every attempted chunk failed; persist a partial outcome and retryable failed-chunk set for mixed results. A successfully processed chunk that contains no entities must remain distinguishable from a provider failure.

### V2-06 — SEVERITY Med — graph claims are acknowledged even when retry/parking was not durable

**Evidence:** Retry scheduling raises on broker failure (`packages/graph/queue.py:352`); `apps/worker/jobs/graph_extraction.py:337` rethrows that failure. `apps/worker/jobs/graph_extraction.py:428` catches any handler exception and proceeds to acknowledgement at line 452. Failed-state persistence swallows exceptions at `apps/worker/jobs/graph_extraction.py:293`. The acknowledgement Lua removes the live claim/token (`packages/graph/queue.py:78`).

**OBSERVED / what:** The consumer does not distinguish a durable scheduled retry/park from a failed attempt to record either. All handler exceptions reach the same acknowledgement path.

**INFERRED / why it matters:** If retry/failed-state persistence fails but the later ACK succeeds, the job has no ready/delayed entry and no recoverable live claim. Its payload can be stranded, or ultimately removed by the max-attempt cleanup (`apps/worker/jobs/graph_extraction.py:465`). This violates acknowledgement-after-durable-outcome semantics.

**Fix shape:** Return a typed durable disposition from the handler and ACK only confirmed success/retry/park. Propagate parking failures and retain the lease for recovery; preferably record disposition and release the claim atomically. Test a failed retry write followed by a successful ACK-capable broker.

### V2-07 — SEVERITY Med — explicit graph requests silently succeed while graph is disabled

**Evidence:** Flag-off returns no retriever (`packages/graph/factory.py:99`). `_graph_leg` returns an ordinary empty list without recording failure when the retriever is absent (`packages/retrieval/orchestrator.py:380`). Explicit graph mode calls that leg (`packages/retrieval/orchestrator.py:464`), and graph-only mode declares no required legs (`packages/retrieval/orchestrator.py:175`). Graph and hybrid_graph remain accepted retrieval enum values (`packages/retrieval/interfaces.py:50`).

**OBSERVED / what:** Disabled graph capability is indistinguishable from a successful graph search with no evidence; hybrid_graph also proceeds without a graph-unavailable disclosure. Even an actual graph-only leg failure is classified as optional.

**INFERRED / why it matters:** Users requesting graph search can receive a healthy empty result or an evidence refusal when no graph search occurred. This undermines flag-off capability honesty, while keeping default HYBRID inert remains desirable.

**Fix shape:** Refuse explicit graph-only requests when disabled/unavailable; disclose graph omission for hybrid_graph. Keep flag-off default HYBRID free of graph work.

**Verified enforcement:** Flag-off retrieval exits before constructing a graph store (`packages/graph/factory.py:99`), and the production worker starts graph consumption only for an enabled mode (`apps/worker/worker/main.py:63`, `packages/graph/consumer.py:66`). The graph supervisor resolves the real extraction loop (`packages/graph/consumer.py:283`). LLM extraction with no key raises instead of selecting rule extraction (`packages/graph/dispatch.py:104`). Missing agent LLM configuration raises an explicit unavailable error (`packages/agents/factories.py:62`), and tool policy is checked before dispatch (`packages/agents/runtime.py:533`).

## V4 — executor, production DI, manifest, checkpoints, migrations

**Verdict REJECT — fake execution has been removed from the inspected production DI, but API durability/cancellation and checkpoint correctness remain incomplete, and transforms still silently succeed on errors.**

### V4-01 — SEVERITY High — production workflow data and recovery state default to volatile stores

**Evidence:** The application defaults drafts to `InMemoryDraftStore` (`apps/api/app/workflows/store.py:25`); approvals and runs are dictionaries (`apps/api/app/workflows/store.py:20`). Every API run gets a new `InMemoryCheckpointStore` (`apps/api/app/workflows/router.py:655`). A separate SQLite backend exists, but its factories call default constructors (`packages/stores/workflow_draft_store.py:670`, `packages/stores/workflow_draft_store.py:682`), whose path default is `:memory:` (`packages/stores/workflow_draft_store.py:73`, `packages/stores/workflow_draft_store.py:508`). The API imports its own store factory (`apps/api/app/workflows/router.py:70`). No production injection of a file-backed draft/checkpoint store was found by targeted symbol search. The SQL migration remains explicitly draft-only (`packages/workflow_engine/migrations/0001_workflow_draft_revisions.up.sql:1`); its tests assert that application Alembic does not reference it (`tests/unit/test_workflow_draft_migration.py:184`).

**OBSERVED / what:** The API's accepted drafts, revisions, approvals, run history, and recovery checkpoints live in process memory. The existence of SQLite classes and scratch migration tests does not change that default or wire them into this API.

**INFERRED / why it matters:** Process restart loses user-authored workflow data and recovery history; multiple API processes can disagree about saved drafts/runs. An engine closed as a product cannot rely on these stores for durable authoring or resume. This does not claim that an upgrade was or was not applied to a live database.

**Fix shape:** Configure and inject durable shared stores for drafts, bound approvals, runs, and checkpoints, with an explicit persistent path/database and fail-closed startup checks. Integrate the chosen schema into its deployment migration path. Verify restart and multi-process reads through the production API factory.

### V4-02 — SEVERITY Med — API runs are invisible and uncancellable until execution has ended

**Evidence:** `apps/api/app/workflows/router.py:656` awaits the entire execution, then registers the run/executor at line 674 and returns its ID at line 676. Status/cancel require an already stored run (`apps/api/app/workflows/router.py:705`, `apps/api/app/workflows/router.py:753`). The cancellation store requests cancellation only on the registered executor (`apps/api/app/workflows/store.py:84`). The lifecycle test cancels only after the run response (`tests/unit/test_v4_authoring_api.py:353`) and accepts an already completed result at line 359.

**OBSERVED / what:** There is no registered active run or exposed run ID during the awaited execution. The normal API path publishes only terminal runs.

**INFERRED / why it matters:** The active-run status and cancel surfaces cannot control an API-started run while it is doing work. The lifecycle test proves terminal cancellation is harmless, not that active execution can be interrupted.

**Fix shape:** Persist/register an initial run and cancellation handle before dispatch, return a run ID, and execute via a supervised task/worker. Persist live state and route cancellation to the active execution owner. Test a blocked node while concurrently polling/cancelling through HTTP.

### V4-03 — SEVERITY Med — production transform failures return unrendered templates as success

**Evidence:** `packages/workflow_engine/production_executor.py:108` formats the template; the broad exception handler at line 109 returns the original template. The executor treats a result without a top-level error as success (`packages/workflow_engine/executor.py:1203`, `packages/workflow_engine/executor.py:1214`) and marks the node COMPLETED (`packages/workflow_engine/executor.py:971`).

**OBSERVED / what:** A template such as `Hello {name}` with input lacking `name`, or an invalid formatting expression, produces literal template text rather than a failed node.

**INFERRED / why it matters:** A malformed transform can propagate placeholders to downstream nodes and complete the workflow even though the requested transformation never occurred. This silent fallback remains in the production executor after fake removal.

**Fix shape:** Raise a typed permanent transform/configuration error naming the node and missing/invalid field. Validate static template/configuration shape during authoring, and cover a missing field through the production API/executor.

### V4-04 — SEVERITY Med — durable checkpoint serialization changes execution values before replay

**Evidence:** `packages/workflow_engine/checkpoint.py:127` truncates every text value to 8,192 characters and applies content redaction; recursive serialization covers node outputs and initial input (`packages/workflow_engine/checkpoint.py:143`, `packages/workflow_engine/checkpoint.py:199`). The SQLite store persists that serialized form (`packages/workflow_engine/checkpoint.py:297`) and reloads it verbatim at line 315. Resume returns stored node output as execution data (`packages/workflow_engine/checkpoint.py:398`). Live node output may be up to 1 MiB (`packages/workflow_engine/executor.py:155`). The exact-resume test uses an in-memory checkpoint (`tests/unit/test_workflow_checkpoint.py:277`) with short fixture outputs; the bounded-checkpoint test explicitly acknowledges per-field truncation (`tests/unit/test_workflow_checkpoint.py:219`).

**OBSERVED / what:** Durable serialization is lossy for otherwise permitted long outputs and for values matching the redaction grammar. The in-memory store retains the original object (`packages/workflow_engine/checkpoint.py:247`), so it does not exercise the same replay values as SQLite.

**INFERRED / why it matters:** A durable resumed run can compute a different downstream result from an uninterrupted run. The “never silently truncated”/exact-resume claims exceed what the cited tests establish. Protecting secrets in logs does not make a redacted value semantically interchangeable with execution state.

**Fix shape:** Separate redacted observability from exact resumable data. Use immutable blob references or appropriately protected execution-state storage; reject non-resumable state before claiming a checkpoint. Test a persisted/reopened checkpoint with an output longer than 8,192 characters and verify exact continuation.

### V4-05 — SEVERITY Med — checkpoint write failure is hidden behind ordinary completion

### V4-06 — SEVERITY Med — resume accepts changed input under the same run identity

**INFERRED / why it matters:** A resumed run can report new input while replaying old results, and the idempotency conflict guard no longer proves that the recorded work matches the delivery. This is a component resume-path defect; the reviewed API currently exposes no resume endpoint.

### V4-07 — SEVERITY Med — SQLite checkpoint append can overwrite a concurrent checkpoint

**Evidence:** `packages/workflow_engine/checkpoint.py:280` reads the next sequence through one connection. Append computes that sequence before opening a separate write connection (`packages/workflow_engine/checkpoint.py:290`, `packages/workflow_engine/checkpoint.py:298`) and writes with `INSERT OR REPLACE` at line 300. The key is `(run_id, sequence)` (`packages/workflow_engine/checkpoint.py:274`).

**OBSERVED / what:** Sequence allocation and insertion are separate transactions; a collision replaces a prior row instead of rejecting it. The store permits multiple instances on the same file.

**INFERRED / why it matters:** Concurrent workers/processes appending the same run can both allocate one sequence, and the later writer silently destroys the earlier recovery state. This contradicts append-only/ordered checkpoint semantics. Same-event-loop single-caller behavior does not cover multiple processes.

**Fix shape:** Allocate and insert in one locked transaction, use INSERT without replacement, and handle stale-writer/sequence conflicts explicitly. Add a two-connection/process collision test that proves no prior row changes.
