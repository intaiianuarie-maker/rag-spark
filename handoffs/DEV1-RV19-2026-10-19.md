CHANGE — **fix choice (a): absolute paths are REQUIRED**
`apps/api/app/agents/lifecycle_routes.py` + `apps/worker/worker/main.py`
(mirrored implementations, pinned by the agreement test):
- New `_absolute_path(value)` returns the absolute path or ``None`` when the
  value is relative.
- `agent_store_readiness()` now refuses a RELATIVE `AGENT_STORE_SHARED_ROOT`
  or `AGENT_STORE_DB` with the coded reason
  **`agent_store_path_not_absolute`** (503 admission refusal / no worker
  consumer) in every environment.
- Rationale: a relative store path is resolved against the **process working
  directory**, so an api and a worker started from different directories
  resolve different databases while both reporting the store as shared
  (reproduced: api 202 + queue depth 1, fresh worker depth 0 / claim None).
  A relative path can never be shared, so it is not admitted at all.
- The **absolute host-mode guard is retained**: a configuration with no
  declared shared mount and ABSOLUTE paths still admits, and an independent
  worker process started from a different working directory sees and claims
  the accepted run (regression
  `test_absolute_store_paths_are_shared_across_working_directories`).
- The compose deployment is unaffected: its defaults
  (`AGENT_STORE_SHARED_ROOT=/app/.agent`, `AGENT_STORE_DB=/app/.agent/agent.db`)
  are absolute.

WHY:
- A relative path makes the store's identity depend on the process working
  directory. The api accepted a run and enqueued it in ITS OWN `state/agent.db`;
  the worker, started elsewhere, opened a different file, saw depth 0 and
  claimed nothing. The absolute-path control in the same probe claims the run
  correctly, which isolates the cause to the path, not to the store.
