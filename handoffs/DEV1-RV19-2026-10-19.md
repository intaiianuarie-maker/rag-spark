CHANGE:

**F1 [P1] T-RV19-01 — verification now covers the exact published content**
`packages/workflow_engine/production_executor.py`:
- New `_split_output_payload(output)` locates the JSON payload inside the raw
  model output with a brace-depth scan (string-aware) and returns the text
  OUTSIDE that block as *residual*. The located block is parsed with the
  existing `answer.prompts.parse_model_output`, so the workflow executor and
  the answer engine agree on the answer/claims shape.
- The structured `answer` field is published content, so it JOINS the
  verification set: it becomes a claim (inheriting the configured reference
  set) unless a claim already covers it. A verifier that only supports the
  model's `claims` can no longer pass an answer it never saw.
- The published output is the **covered representation** (`_covered_representation`):
  the answer text, else the claims' text, else the prose. The raw model
  payload is never published.
- Residual prose (prefix/suffix around the JSON) is rejected: the node result
  is `verified=False`, `verification_stage="uncovered_output"`,
  `verification_reasons=["uncovered_output_text"]`, and the wrapper prose is
  not part of the published output.
- The `verified` flag remains the gate: `verified=True` / `"Stage 11 & 12"`
  only when Stage 11 **and** Stage 12 pass over the published content.
  (Withholding the whole output was implemented first and then reverted: the
  V4 live-scenario battery in `evals/eval_v4_workflow_live_scenarios.py` —
  outside my allowed files — requires the node text to reach the output node.
  The published text is now always the content that was submitted for
  verification, and the verdict states whether it passed.)

**F4a [P1] T-IMP-001 — admission resolves the RESOLVED settings**
`apps/api/app/agents/lifecycle_routes.py`:
- New `agent_store_readiness()` returns `(admit, shared, reason, path,
  environment)`. The environment comes from `core.config.get_settings()`
  (process env **or** `.env`), never from a raw `os.environ` read.
- `POST /v1/workspaces/{ws}/agent/runs/queued` refuses with **503** and a
  machine-readable `error` (`agent_store_not_configured` /
  `agent_store_unshared`) BEFORE the run record is persisted.
- `apps/api/app/main.py` resolves the same readiness at startup and installs
  the store only when the verdict allows it; otherwise it logs
  `agent_store_unavailable` (error) instead of silently running in-memory.

**F4b [P1] T-IMP-001 — the agent DB is wired to a shared, validated volume**
- `docker-compose.yml`: new named volume `agentdata`, mounted at `/app/.agent`
  in BOTH `api` and `worker`; `AGENT_STORE_DB` now defaults to the shared
  path `/app/.agent/agent.db` and `AGENT_STORE_SHARED_ROOT` is published as
  `/app/.agent`. A configured path outside that root is refused by the
  application (two containers, two filesystems).
- `apps/worker/worker/main.py`: the worker resolves the same readiness and,
  when the store is not shared/durable in production/staging, logs
  `agent_store_unavailable` + `agent_consumer_disabled` and does NOT start the
  agent consumer (it must not consume from a store the API does not share).
- The worker cannot import the API package in its container image, so the two
  implementations are pinned against each other by
  `test_api_and_worker_readiness_agree` (identical verdict for six
  environment/path combinations).
- `.env.example`: documents `AGENT_STORE_SHARED_ROOT` / `AGENT_STORE_DB`.

WHY:
- F1: the executor checked only the model's `claims` while publishing the
  entire raw output. A verifier supporting only the budget statement yielded
  `verified=true` / `"Stage 11 & 12"` for an answer ("The moon is made of
  cheese") it never saw, and prose around tolerated JSON survived publication.
- F4a: admission read raw `os.environ["APP_ENV"]` while the application logs
  the RESOLVED environment. A temporary `.env` with `APP_ENV=production` and
  no `AGENT_STORE_DB` logged production and still returned HTTP 202 into
  `InMemoryAgentRunQueue` (parent depth 1, separate worker depth 0).
- F4b: a non-empty `AGENT_STORE_DB` did not establish shared storage — the
  api/worker services shared only `/app/.graph` and `/app/.workflow`, so the
  agent DB landed in separate container layers (durable SQLite queue at depth
  1 versus 0 across two filesystems).
